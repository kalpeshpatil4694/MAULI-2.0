2. COMMAND → RESULT → PRODUCT WORKFLOW (verified end-to-end)
────────────────────────────────────────────────────────────
  POST /api/command
    ├─ rate limit check (5/min/IP)
    ├─ queueCommand():
    │    • 1 AI call  → interpretWithAI (planning; falls back to
    │      deterministic freePlanFromCommand if AI quota/error)
    │    • createProject  → 1 D1 write
    │    • ~6-9 tasks created (research, product-planning, backend,
    │      database, frontend, security, testing + final QA) → 6-9 D1 writes
    │    • memory remember() → 1 D1 write
    │    • approval gate if high-risk
    ├─ saveCommandResult → 1 D1 write
    └─ ctx.waitUntil(schedulerTick) → executes the project chain:
         claim task → executeTask → verifyResult → complete/fail task
         • internal.plan tasks (research/planning/QA): NO AI — deterministic
         • internal.code tasks (frontend/backend/database/security):
           up to 3 AI calls × max 8,000 tokens each
         • per task: runs + events + verifications + agent updates
           + memory + artifact writes (~10-15 D1 writes per task)
    └─ finalizeCommand → buildFinalDelivery (final-delivery artifact
       with download path) → saveCommandResult

  PRODUCT DELIVERED WHEN:
    • all tasks completed AND final QA task passed AND
    • for code projects: security task completed with verificationId
    Otherwise delivery is BLOCKED by design (defense in depth).

  ✅ CONCLUSION: The pipeline DOES deliver a product (code-workspace
  artifact + final-delivery manifest + optional APK/EXE via GitHub
  Actions build). BUT the delivery was VERY slow and fragile:

  ❌ BUG FOUND & FIXED: schedulerTick ran only ONE task per project
     per tick. A 7-9 task command therefore took 35-45 minutes
     (one task every 5-min cron). The user re-sent commands because
     "nothing happened" — and each re-send burned more AI + D1 quota.
     FIX: the founder-command/approval triggers now drain the full
     task chain (up to 8 tasks) for that project immediately. Product
     now arrives in minutes, not ~40.

    • /api/state poll (every 60s, PUBLIC, unauthenticated):

      ≈ 1,400 rows × 288 = ~400,000 rows/day ⚠️

    • cron hydration: skipped when store hydrated ✅
    Old deployed code (pre-optimization) was far worse: hydrate +
    prune + ensureSchema per request ≈ 2,600 rows per hydration —
    this is what blew the 5M limit twice.

  AI CALLS (neurons/day free = 10,000):
    per command ≈ 1 planning + up to 3 × code tasks
    A typical web-app command = 4-7 AI calls × (input ~1.5-2k +
    output up to 8k tokens) ≈ 30,000-70,000 neurons/command
    ❌ FREE AI QUOTA CAN BE EXHAUSTED BY 1-2 COMMANDS.
    After quota: code tasks fall back to app-templates (still
    functional apps, but generic) — no hard crash.
    Workers AI paid tier ≈ $5/mo → ~25x more neurons.

4. WHAT CAUSED THE RECURRING 5M rows_read LIMIT HITS
─────────────────────────────────────────────────────
  a) Dashboard polls /api/state every 60s → 5-6 full D1 SELECTs each
     time, even though memory had identical data (redundant read).
  b) /api/state and /api/usage were PUBLIC with no rate limit —
     any visitor/bot could hammer them.
  c) Old deployed code (pre-commit 4533882) hydrated + pruned +
     ensured schema on nearly every request (~2,600 rows each).
  d) Repeated commands (because delivery took ~40 min) multiplied
     AI + D1 usage.
  e) cron schedulerTick 1-task-per-tick made (d) worse.

     returned 0 projects even though D1 reads WORKED (limit had reset).
     Cause: hydrate() had a _d1Failed flag that was never cleared — the

9. D1 rows_read BLEED + AGENT DUPLICATION (2026-09-19) — ROOT CAUSES & FIXES
──────────────────────────────────────────────────────────────────────────
  Measured on the live Worker: /api/state was returning 2.5 MB of data and
  reading ~3.2K rows per call while /api/health reported hydrated:false.

  ROOT CAUSES
  a) HYDRATION NEVER COMPLETED. initOnce() started store.hydrate() without
     ctx.waitUntil, so the isolate was torn down mid-hydration; _initialized
     was already true, so it was never retried. The store therefore stayed
     cold for the isolate's whole life and every /api/state poll took the
     cold-isolate path: 5 full-table reads ≈ 3.2K rows × 1,440 polls/day
     ≈ 4.6M rows_read/day — the entire 5M/day free budget, with no user
     activity at all.
  b) AGENT DUPLICATION. seedAgents() only checked the in-memory store, so
     every cold isolate start inserted 18 brand-new agent rows. Measured
     growth: 1,090 → 2,649 agents in ~24h (~77 cold starts).
  c) DEDUPE AND PRUNE NEVER RAN. dedupeAgents() and pruneEvents() each built
     a single DELETE binding thousands of parameters; D1 rejects statements
     with more than 100 bound parameters, so both failed silently and the
     duplicates (and the 500K-row events table) were never cleaned.
  d) eventStats() ran COUNT(*) + SUM(LENGTH(payload)) over the whole events
     table on every usage refresh — a full ~500K-row scan.
  e) STORAGE 93% FULL. command_results held 8,592 rows / 175 MB and the
     cleanup path (cleanupD1) failed for the same 100-parameter reason.

  FIXES (commit d2f223d / 6451fa0 / e437c32)
  ✅ /api/state now serves memory when hydrated, otherwise a 5-minute cached
     bounded snapshot (agents ≤200, tasks ≤600, approvals ≤100) — a repeat
     poll inside the cache window costs 0 extra rows.
  ✅ Hydration runs via ctx.waitUntil and is single-flight (store.hydrateOnce),
     so concurrent light-path requests cannot each re-read every table and
     the store actually converges to memory-served data (0 D1 reads).
  ✅ Built-in agents use deterministic ids (agent-builtin-*) and seeding
     writes nothing before hydration → re-seeding is an idempotent upsert.
  ✅ All pruning deletes are set-based (row cap inside the statement) or
     chunked, honouring the 100-parameter and ~50-queries-per-invocation
     limits. New pruneOldResults() keeps the newest 300 command results plus
     recent runs/verifications/builds.
  ✅ Cooldowns and daily delete budgets live in a single D1 row, because
     Cloudflare recycles isolates and runs concurrent crons — per-isolate
     counters cannot bound the account-wide rows_written budget.
  ✅ eventStats() samples a bounded 1,200-row window instead of scanning the
     whole events table; hydration has per-type row caps.

11. DELIVERY BLOCKED + DAILY LIMITS (2026-09-24) — ROOT CAUSES & FIXES
───────────────────────────────────────────────────────────────────────
  SYMPTOMS (user report): commands show "active" but no product is ever
  delivered, no final result is written, and a Cloudflare limit is
  exhausted every day.

  MEASURED
    • Last 50 command results: 49 "failed" ("One or more tasks failed
      after recovery/retry limits"), 1 stuck "queued" since 2026-09-21.
    • Failed tasks show attempts: 26 with error "Execution lease expired".
    • Live state: 51 projects stuck "active", 51 blocked + 16 working +
      30 queued tasks; only 367/685 tasks completed.
    • /api/health d1Quota reported 0/100,000 used while real usage was
      over budget — the quota counters are per-isolate (env var) and
      reset with every cold isolate, so the dashboard could not see it.
    • CF API: D1 storage 165 MB (33%) — the events table is regrowing;
      Worker size 3.00 MB (at the 3 MB free limit alert).

  ROOT CAUSES (each verified against code + Cloudflare docs)
  a) waitUntil 30 s WALL. Cloudflare: "waitUntil() can extend execution
     for up to 30 seconds after the response is sent". The whole project
     chain was drained inside waitUntil after POST /api/command, and code
     tasks (up to 3 Workers AI generations) exceed 30 s → the invocation
     is CANCELLED mid-run, leaving the run stuck in 'running'.
  b) LEASE RECOVERY BURNED REAL ATTEMPTS. Every cancellation became
     "Execution lease expired" + attempts+1, so after a few platform
     kills the task was permanently failed — this is why commands ended
     as "failed after recovery/retry limits".
  c) ORPHANED TASKS WERE UNRECOVERABLE. RUNNABLE = {queued, assigned} and
     recoverStaleTasks only scanned runs. A task left in working/
     assigned/verifying with no live run (cancelled invocation) could
     never be picked up again → hasRunning stayed true forever →
     finalizeCommand never wrote a result → project "active" forever.
  d) WRITE STORM — daily rows_written (100K/day). seedAgents() patched
     ALL ~19 built-in agents (row + full agent event = ~38 D1 writes)
     on every isolate start and gate creation. Cold isolates every
     minute ⇒ >100K rows_written/day by itself.
  e) READ STORM — daily rows_read (5M/day). Cron changed to every minute
     (2026-09-23) × full hydration (~2-3K rows) ≈ 4.3M rows/day before
     any dashboard traffic.
  f) CPU 10 ms. Free plan allows 10 ms CPU per cron trigger and per HTTP
     request. Hydration + 40 projects × multiple full task-table scans
     per tick (scheduler + ensureProjectPipeline + finalize) risked
     exceededCpu kills — which also produced (a)'s orphaned runs.
  g) AI OUTPUT ALWAYS TRUNCATED. ai.js clamped max_tokens to 1200 while
     the executor requested 8000 → every generation produced invalid
     JSON → 3 wasted AI calls per task (burning neurons) → silent
     template fallback.

  FIXES (this change set)
  ✅ src/worker.js — command/approval/chat drains now pass budgetMs
     20 000: new tasks are only STARTED inside the 20 s waitUntil
     window; the rest stays queued for cron (which has a 15-min wall
     limit, budgeted to 8 min per tick).
  ✅ src/scheduler.js — lease expiry is now an INFRASTRUCTURE recovery:
     attempts are NOT consumed (separate infraRecoveries, capped at 8).
     New orphan recovery requeues any working/assigned/verifying task
     without a live run (15 s grace), so projects can always reach a
     final result. Single per-tick task index (one scan instead of
     multiple full-table scans per project) for the 10 ms CPU budget.
     Cron advances up to 6 runnable tasks per project per tick.
  ✅ src/pipeline-gates.js — accepts the scheduler's task index; gate
     creations/conversions are synced back into it (no rescans).
  ✅ src/agents.js — seedAgents is quiet: heartbeat-only refreshes are
     throttled to 5 min and emit no event; unchanged agents are skipped
     entirely. Cuts the ~38-writes-per-isolate storm to near zero.
  ✅ wrangler.jsonc — cron reverted */5 (288 hydrations/day instead of
     1 440; founder-command/approval paths still drain instantly).
  ✅ src/ai.js — max_tokens clamp 1200 → 3000 so generated artifacts can
     actually be valid JSON; src/functional-code-executor.js — 3 → 2
     attempts with a 40 s per-attempt timeout → falls back to templates
     instead of dying with an expired lease.
  ✅ tests/pipeline-recovery.test.js — 5 regression tests (quiet seeding,
     orphan requeue, attempt-neutral lease recovery, cancellation cap,
     live claim left alone). Suite: 151/151 pass; wrangler dry-run OK.

SECTION 13 — D1 ROWS_WRITTEN DAILY CAP AUDIT (2026-09-28)
Alert: "D1 operations are nearing the daily cap — rows_written,
limit 100,000, 95% reached."

ROOT CAUSES FOUND (each one multiplied by isolate count)
  1. src/tools.js — registerTool() wrote registeredAt: now() on every
     call. ensureBuiltinTools() runs on EVERY isolate start, so all
     ~32 built-in tool rows counted as "changed" on each cold start.
     Hundreds of isolates/day x 32 rows = the single biggest
     amplifier. store.put() already skips no-op writes, so the only
     thing making them "changed" was the fresh timestamp.
  2. src/store.js — 11 high-frequency telemetry event types
     (agent.updated, execution.*, memory.created, tool.executed,
     chat.*, agent.activity, sub_agent_created, duplicate_prevented)
     were written to D1 AND then deleted again by pruneEvents().
     Each event cost 1 write on insert + 1 write on delete.
  3. src/agents.js — seed heartbeat every 5 min per agent x every
     agent x every isolate that hydrated.
  4. src/execution.js — running-task heartbeat every 30 s; a single
     long run could burn thousands of rows in one execution.
  5. src/tasks.js + src/scheduler.js — completeTask()/failTask()
     each did a second store.put('tasks', …) just to attach
     verificationId after the fact: 2 writes per task finish.
  6. src/db.js — pruneEvents/pruneOldResults DELETEs also count as
     rows_written; caps were 8 000 + 50 000 + 30 000 = up to 88 000
     rows/day of pure deletion.

FIXES APPLIED
  ✅ src/tools.js — registerTool() reuses existing registeredAt and
     createdAt, so a warm isolate re-registers 0 rows.
  ✅ src/store.js — MEMORY_ONLY_EVENTS set (the 11 types above) keeps
     them in the in-memory activity feed but skips D1 entirely;

16. ANDROID APK BUILD PATH (2026-09-28) — "GIVE ME A COMMAND AND I GIVE
    YOU AN APK" WAS NOT TRUE. HERE IS WHY, AND WHAT WAS FIXED.
────────────────────────────────────────────────────────────
  The question was whether a command could end in a real APK file on an
  Android phone. It could not. The dashboard showed 📱 APK buttons, the
  route existed, the workflow text was generated — and no build ever ran.

  SYMPTOM
    POST /api/build-app returned
      404 {"message":"No code artifact found for this project. Run the
            command first."}
    for projects that /api/state confidently reported as hasCode:true and
    that /api/app-files happily returned 30 files for. No GitHub Actions
    run was ever created for any build.

  ROOT CAUSE 1 — the build never had a workflow to run
    /api/build-app pushed the generated project files to
    build/project-<id> and then tried to push its own copy of
    .github/workflows/build-apps.yml, so that pushing files would trigger
    a build. That PUT's response was never inspected:

      await fetch('.../contents/.github/workflows/build-apps.yml',
                  { method:'PUT', ... });   // no .ok check, no error

    Writing under .github/workflows needs a token scope the worker's
    GITHUB_TOKEN does not have, so the PUT failed every time and the
    failure was discarded. The branch ended up with www/ and friends and
    no workflow — and the API replied "8 files pushed to GitHub. Build
    will start shortly.", which was untrue. No run, no APK, forever.
    Confirmed on the live worker: after a real build the branch had
    www/index.html, www/app.js, www/styles.css and no build-apps.yml,
    while `gh run list --branch <build branch>` was empty.

  ROOT CAUSE 2 — the routes read a row-capped cache written by another isolate
    /api/build-app, /api/app-files, /api/preview-app and /api/build-status
    all resolved their data from store.list(...). That store is a hydrated
    cache with per-type row caps (artifacts 600, builds 200) and, on a cold
    isolate, is empty until hydration finishes. initOnce() started
    hydration with ctx.waitUntil and returned immediately, so the first
    requests of every new isolate were answered from that empty store:
      • a project whose files were already in D1 reported "no code
        artifact", while /api/state (a separate D1 path) said hasCode:true;
      • /api/build-status answered 404 "Build not found" for a build that
        existed and was mid-flight on GitHub.
    Live evidence: polling one buildId gave 404, 404, 200, 404, 200, 404,
    200 — the same build, alternating, purely on which isolate answered.

  FIXES
    ✅ .github/workflows/build-apps.yml now lives in the repository and
       triggers on `push` to `build/**`, so the file pushes the worker can
       already make are enough to start packaging. It runs Capacitor,
       builds a debug APK, verifies it and uploads it as the
       `android-apk` artifact. concurrency + cancel-in-progress collapses
       the run storm caused by pushing the project one file at a time.
    ✅ initOnce() now awaits store.hydrateOnce() instead of backgrounding
       it. Same tables, same cost, but no route can be answered from an
       unhydrated store any more. hydrateOnce() is single-flight, so only
       the first request of an isolate pays.
    ✅ /api/build-app resolves its artifact list through
       projectCodeArtifacts(), which falls back to a direct D1 query when
       the cache has nothing for the project, and hands that list to
       collectProjectFiles() so the authoritative artifacts are what gets
       pushed rather than a second cache read.
    ✅ findBuild() falls back to a direct D1 read by id, so a build
       started on a previous isolate still has a status.
    ✅ /api/build-app now refuses early (422) when the project has no
       www/index.html or no package.json, naming the actual files it did
       find — instead of pushing a branch whose build was always going to
       die on `test -s www/index.html`.
    ✅ collectProjectFiles() de-duplicates repeated paths, newest content
       winning. /api/app-files returned 30 entries for 8 real files.
    ✅ tests/build-app-source-lookup.test.js (8 tests) locks all of this in.

    not: the earlier test used a truncated project id
    (project_a191fe03-cd96-4ce6 instead of the real

  STILL OPEN

21. WHY THE BUILT APP WAS NOT THE APP (2026-09-29)

  REPORTED
    "Application banun pan perfect banat nai he" — the app builds, but what comes out

  EVIDENCE

        {"generatedBy":"app-templates","template":"game-app","fileCount":1,

  ROOT CAUSE 1 — the AI budget was smaller than the free neuron allowance
    ai.js refused a request after 20 per isolate-day, and code ran on
    @cf/meta/llama-3.3-70b-instruct-fp8-fast: 26,668 neurons/M input and 204,805/M

    neurons a day, i.e. ~17 generations. The pipeline plans with AI first, so a few
    tasks per project exhausted it, every later code task threw (aiError "{}" is a
    plain Error, not an AiError), and functional-code-executor.js silently fell back
    to a template. The user saw a placeholder APK and no error.
    FIX: code() now asks for @cf/qwen/qwen3-30b-a3b-fp8 (4,625 / 30,475 neurons per M
    = ~85 neurons per app, ~6.7x the apps per day), overridable with MAULI_CODE_MODEL,
    and falls back to MAULI_MODEL once if that model is unavailable instead of giving
    up on AI. Budget raised to 100 requests / safety 90, and
    FREE_LIMITS.workersAiSafeRequestsPerDay in db.js follows it.

  ROOT CAUSE 2 — the fallback pages were not apps
    app-templates.js 'web-app' and 'game-app' emitted the marketing page above; the
    'portfolio' case had no generator at all. So every unmatched or AI-starved
    project shipped a page that described an app instead of being one.
    FIX: 'game-app' is now a real chess board (64 squares, legal move generation for
    every piece, captures, turn switching, undo, move log, new game; king capture
    ends the game) and tic tac toe for other games; 'web-app' is a working list app
    (add/complete/search/delete, localStorage); 'portfolio' is a real page with a
    working contact form.

  ROOT CAUSE 3 — the build pushed the OLDEST copy of every file
    collectProjectFiles() collapsed repeated paths with
        for (const f of files) unique.set(f.path, f);
    i.e. the LAST copy wins, while the artifact pool arrives NEWEST-FIRST (D1 orders
    by updated_at DESC). /api/build-app therefore pushed the oldest version of every
    file to the build branch: the dashboard showed one app and the APK contained
    another. Proven live: after POST /api/edits wrote the new chess app into the
    newest artifact, GET /api/app-files (the same authority the build uses) still
    returned the old placeholder.
    FIX: sort the pool by createdAt (the artifact /api/build-app treats as latest)
    and keep the FIRST copy of each path, so the result no longer depends on the
    order the caller hands the artifacts over.

--------------------------------------------------------------------------------

      only re-queued tasks that were already live; a task parked as 'blocked' with
      `blockedReason: 'dependencies incomplete'` was never revisited, so the chain had
      no runnable entry point.

    task -> queued with agent/lease/infra-recovery/error cleared, and every blocked or
    failed task re-activated when its dependencies are terminal OR were themselves
    re-queued in the same pass. It returns { approval, project, requeuedTaskIds }.

    owns it and is the only layer that can read the request body. worker.js keeps its

24.2 STUCK-PROJECT MECHANISM
--------------------------------------------------------------------------------
src/maintenance.js recoverStuckProjects({ dryRun })
  Diagnoses every non-terminal project and returns a per-project verdict:
    awaiting_approval  -> a human gate is open; never touched
    no_tasks           -> plan never landed / was pruned; reported, not invented
    finalize_completed -> every task terminal but the row missed finalization -> set completed
    in_progress        -> a runnable task or a live run exists; left alone
    would_requeue      -> dry run only
    requeued           -> dead chain re-activated through approveProject()
    requeue_failed     -> governance refused; needs manual look
  Idempotent: a second pass reports `in_progress` for anything it just re-queued.
  Exposed as POST /api/maintenance/recover-stuck (founder-authenticated, { dryRun }).
  runMaintenance() (the */5 cron) now self-heals with it, throttled to once per 30 min,
  BEFORE schedulerTick so the recovered work is picked up in the same invocation.
